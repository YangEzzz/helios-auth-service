# 公司组织与部门分类设计

更新日期：2026-11-03

状态：根据最新需求收敛的设计草案，尚未实现。

本方案取代《组织与数据权限设计》。此前有关部门数据隔离、共享授权、负责人继承查看和公司最高负责人查看范围的设计全部不再作为开发依据。

## 1. 目标

维护单公司的多级部门与成员关系，为各业务子系统提供统一部门分类。部门用于表达归属、筛选和统计，不作为业务访问权限依据。

公司用户能否进入某个系统、能否查看某项资源、能否编辑或删除，继续由该子系统现有规则决定。不因资源归属某部门而阻止其他部门访问，也不因此自动放开已有私有数据或系统访问限制。

本次仅更新设计文档，不修改数据库、业务代码或接入现有系统。

## 2. 功能边界

第一版包括：

- 多级部门：新建、改名、调整上级、排序、启用与停用。
- 部门成员：用户可加入多个部门，不分主次。
- 部门负责人：可选，可多人，作为组织信息展示，不自动获得业务系统权限。
- 部门查询：提供稳定部门 ID、名称、层级和状态，供子系统以后接入。
- 管理记录：记录部门结构和人员归属调整，便于追溯。

第一版不实现部门数据 ACL、公开／受限模式、跨部门共享、按部门拦截业务请求、公司最高负责人业务查看特权或权限策略同步。部门分类不能用于限制其他部门查看数据。

## 3. 职责划分与通用对象

| 部分 | 负责内容 |
| --- | --- |
| Helios | 部门、人员与部门关系、负责人展示、组织维护 |
| 子系统 | 创建业务资源、保存资源的部门分类、筛选统计、原有功能与访问权限 |

“资源”只是统称，不要求各系统使用同一种业务对象：术语系统创建词条，工单系统创建工单，知识系统创建文档，资产系统登记资产。Helios 不创建这些业务资源，也不保存所有业务数据。

部门成员关系和资源分类是两回事：某人属于研发部，不意味着他创建的全部资源自动归研发部。尤其多部门用户没有主部门，不能从成员列表中随意取第一个部门作为资源分类。

## 4. 部门分类规则建议

以下为第一版的简化默认设计，后续子系统接入时按业务确认：

1. 每项参与分类的资源关联一个部门，允许“未分类”；暂不支持一条资源选择多个部门。
2. 在子系统使用 department_id 保存分类，名称由部门目录解析；改部门名称不要求批量改业务数据。
3. 分类不要求操作者属于所选部门。只要子系统允许其修改分类，即可选择有效部门；成员关系可以用于推荐选项，但不构成限制。
4. 新建时显式选择部门或保持未分类；若业务上已有明确父对象，可由子系统约定继承父对象分类，但不能由通用模块猜测。
5. 用户调部门不自动修改历史资源分类。
6. 修改资源分类不改变资源的读写权限。分类修改资格由子系统定义，不附加负责人专属规则。
7. 部门筛选默认精确匹配；需要时提供显式“包含下级部门”选项。该开关只影响查询结果，不影响访问资格。
8. 跨部门统计也受子系统原有访问范围约束，不能借统计接口暴露本来不可见的数据。

单部门分类是降低复杂度的建议，不是从“用户可多部门任职”推导的限制；以后若确有跨部门资源分类需求，再改为多对多关系。

## 5. 具体例子

假设小张属于研发部，小林属于产品部，小王同时属于研发部和测试部。

| 场景 | 行为 |
| --- | --- |
| 小张在术语系统创建词条，选择研发部 | 词条被归为研发部分类；原有查看权限不变 |
| 小林进入术语系统，筛选研发部 | 可以看到原本有权查看的研发部词条，不因他属于产品部而被额外屏蔽 |
| 小林想编辑研发部词条 | 只看术语系统是否允许编辑；部门不参与授权 |
| 小林有权修改分类，将词条改为产品部 | 只改变归类，不自动改变查看和编辑权限 |
| 小王新建词条 | 可选择有效部门或未分类，不自动指定“主部门” |
| 小张在工单系统创建工单，选择测试部 | 工单分类为测试部；是否能提交或修改由工单系统决定 |
| 同一个用户在不同系统拥有不同角色 | 各系统分别执行原有角色规则，部门不统一授予编辑或删除能力 |
| 小张从研发部调到产品部 | 历史词条仍分类为研发部，不自动跟人移动 |
| 研发部负责人查看财务部资源 | 与普通用户一样，由子系统原有权限决定；负责人身份不扩大查看范围 |
| 某系统原有私有资源标记为研发部 | 仍然私有，部门分类不会将它公开 |
| 筛选技术部，选择包含下级 | 返回技术部及其下级部门分类且当前用户原本有权查看的资源 |
| 清空部门筛选 | 返回当前用户原本有权查看的全部分类资源，不等于全库无权限过滤 |

## 6. 表结构草案

Helios：

| 表 | 核心字段 |
| --- | --- |
| departments | id、parent_id、code、name、sort_order、status、created_at、updated_at |
| department_memberships | id、department_id、user_id、is_manager、created_at、updated_at；department_id + user_id 唯一 |
| organization_audit_logs | actor_id、action、target_type、target_id、before、after、created_at |

负责人必须是该部门成员，退出部门时移除负责人标记。部门树禁止循环；部门 code 唯一，ID 保持稳定。组织维护复用 Helios 现有受保护管理能力，不额外引入业务数据权限角色体系。

子系统：在参与分类的业务表中增加可空 department_id 即可。若以后选择集合继承，应只维护明确的分类来源，避免父子重复字段失去一致性。业务数据留在各自数据库，不新增中央资源库或 ACL 表。

## 7. 部门生命周期与历史数据

有下级部门时不能直接停用父部门；停用前先处理有效成员和负责人。部门不做物理删除，以稳定 ID 保留历史资源分类，避免为停用部门而依赖扫描所有子系统数据库。

停用部门不再出现在新建分类选项中；历史资源仍显示部门名称和停用标识，仍能通过历史筛选查询。已有资源可以由有资格的用户改为其他有效部门或未分类，不要求停用时批量迁移全部资源。

部门改名不改变分类关系；部门改挂上级不改变直接归类，但“包含下级”的筛选结果和统计口径随当前层级变化。第一版不提供历史时点组织结构统计。

## 8. 接口与页面规划

Helios 提供部门树查询、部门维护、成员维护接口，沿用现有身份认证和管理入口。部门目录只返回各系统使用所需的字段，不因为分类需求向所有调用方开放完整成员个人资料。

子系统接入仅需：

- 在业务表单提供部门分类选择。
- 在列表提供部门筛选和可选的“包含下级”。
- 在详情或列表显示部门标签。
- 原有接口保存和返回 department_id，保存时验证部门有效。

不新增“公开／受限”“共享人员”或“部门查看权限”弹窗。无权限用户不能借分类修改接口绕过原有业务编辑限制。

部门目录可以采用简单缓存；新保存分类时以可信目录验证部门状态。目录暂时不可用时，历史资源读取继续按原有权限工作并可使用已有名称缓存；无法验证的分类变更返回可重试错误，不把分类故障升级成所有业务数据读取失败。

## 9. 与现有数据兼容及实施顺序

现有 users.department 是字符串，未来需由管理员确认映射到部门目录，再导入多部门关系。迁移不根据字符串推断负责人，不改现有项目成员和子系统角色。

现有资源先保持未分类，不按创建人的当前部门批量推断历史归属；需要补分类时，由各系统提供预览与确认流程。

实施顺序：先评审本方案，再开发 Helios 部门和成员管理；随后选择一个子系统接入分类选择和筛选。其他系统按需接入，任何一步都不引入部门数据隔离。

## 10. 验收重点

- 多部门成员没有主次，负责人不自动获得业务特权。
- 同一资源修改部门分类前后，原有访问和操作权限保持一致。
- 非本部门用户可以筛选其他部门，结果受子系统原有访问权限约束。
- 普通业务用户不能通过分类字段篡改接口绕过原有角色检查。
- 改名、停用和人员调动不丢失历史资源分类。
- 分类目录故障不阻断已存在业务资源的正常读取。

本方案统一的是组织目录与部门分类，不统一各子系统的业务资源模型，也不改变其原有权限制度。
