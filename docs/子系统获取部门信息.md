# 子系统获取部门目录与当前用户归属

日期：2026-11-03

## 接口

现有 SSO 接口新增字段，旧字段及登录协议保持兼容：

- POST /api/sso/exchange：子系统后端使用项目 HTTP Basic 凭据、一次性授权码和 PKCE 校验原文换取身份，同时取得部门信息。
- POST /api/sso/identity：子系统后端使用同一项目 HTTP Basic 凭据，提交 `{ "user_id": "已验证本地会话中的 Helios 用户 UUID" }`，重新读取身份、项目角色及部门信息。

两个接口都先验证应用凭据、账户有效性和该用户的项目访问资格。没有项目资格时不会返回部门数据。项目密钥仅放子系统后端，不能发给浏览器。

## 返回结构

以下 ID 为结构示意；实际 ID 均为稳定 UUID：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "user": {
      "id": "user-uuid",
      "name": "示例用户",
      "email": "user@example.test",
      "avatar": "",
      "role": "user",
      "departments": [
        { "id": "rd-uuid", "name": "研发部", "status": "active", "is_manager": true },
        { "id": "qa-uuid", "name": "测试部", "status": "active", "is_manager": false }
      ]
    },
    "project_id_string": "example-project",
    "role_in_project": "member",
    "organization": {
      "version": "部门目录内容的 SHA-256 摘要",
      "departments": [
        { "id": "tech-uuid", "parent_id": null, "name": "技术部", "sort_order": 0, "status": "active" },
        { "id": "rd-uuid", "parent_id": "tech-uuid", "name": "研发部", "sort_order": 1, "status": "active" },
        { "id": "qa-uuid", "parent_id": "tech-uuid", "name": "测试部", "sort_order": 2, "status": "active" }
      ]
    }
  }
}
```

user.departments 是当前用户的全部直接归属，不分主次，也不把祖先部门自动当成成员关系。is_manager 仅为相应部门负责人标记。organization.departments 是公司部门目录，包含停用状态以解析历史分类；新分类选项应只显示 active 部门。

目录不包含其他用户、各部门成员名单、成员数量或操作日志。注册时自由填写的部门文本不是正式归属来源。为兼容尚未补齐归属的历史账户，用户部门允许返回空数组，不猜测分配。

## 后续更新

登录交换和每次 identity 查询都读取最新数据库状态，并将组织目录和成员关系作为同一份组织状态读取。人员调部门、负责人变化、部门改名或移动后，子系统通过下一次 identity 查询获取新值。

organization.version 只描述目录，不能用于判断用户归属是否变化。即使目录版本相同，也必须处理每次响应的 user.departments。版本是比较值，不是访问令牌，也不是业务权限。

子系统建议在当前用户资料加载或显式刷新时，由自己的后端查询 identity，再把必要字段返回自己的前端；离职、项目准入等校验继续沿用现有身份检查策略。Helios 不主动推送变化，不会自动更新子系统已经复制到本地的数据或长期令牌。

## 接入范围

本次在 Helios 提供登录返回与刷新能力，并更新接入说明；不修改 Atlas、Nexus 等系统的业务表和页面。现有子系统若使用固定结构反序列化或只复制部分字段，需要按本文扩展数据结构与自己的用户资料接口，才能展示这些新增信息。

部门信息只用于组织展示、分类、筛选和统计。查看、编辑、删除仍按子系统原有规则执行，不从部门负责人标记推断项目管理员身份。
