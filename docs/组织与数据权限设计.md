## 1. 目标与实施边界

在 Helios 中建设边界独立的组织与授权模块，管理单公司的多级部门、平等的多部门成员关系、部门负责人及公司最高负责人，为将来的业务系统提供一致的数据可见性规则。

本阶段只定设计，不修改业务代码、数据库和运行配置，不接入 Atlas 或其他子系统。后续组织功能可以先独立交付；在业务系统完成接入前，组织配置不会自动改变其数据访问行为。

不包含多公司、多租户、人事薪酬、考勤、审批和通用自定义角色引擎。

### 1.1 通用术语与职责

本方案的权限对象统一称为“资源”，即子系统中需要控制访问的一项业务对象，不要求它是手册、文档或容器。创建资源发生在对应业务子系统中，Helios 不提供统一的业务内容创建入口。

| 术语 | 精确定义 |
| --- | --- |
| 子系统 | 经 Helios 登记的应用，使用稳定的 system_id；与现有项目登记如何映射，在接入时确认 |
| 资源类型 | 该子系统声明的稳定类型编码 resource_type，不使用中文展示名称当标识 |
| 资源 | 使用 system_id + resource_type + resource_id 定位的业务对象 |
| 操作 | 由子系统定义并校验的 action，如读取、编辑、审核、发布、关闭；并非每种资源都支持全部操作 |
| 权限策略 | 资源的归属部门、公开或受限模式、额外共享对象和版本 |
| 权限策略单元 | 一份策略的作用对象；可以是一条资源，也可以是由多条资源共同引用的业务集合 |

例如下面是拟议映射，不代表这些系统已经完成接入：

| 示例子系统 | 谁创建什么 | 资源类型示例 | 业务操作示例 |
| --- | --- | --- | --- |
| 术语系统 | 用户在术语系统创建词条 | term_entry | 读取、编辑、审核、发布 |
| 工单系统 | 用户在工单系统提交工单 | ticket | 读取、分派、处理、关闭 |
| 知识系统 | 用户在知识系统创建文档 | document | 读取、编辑、发布、归档 |
| 资产系统 | 用户在资产系统登记资产 | asset | 读取、更新、领用、报废 |

Helios 统一提供组织事实；通用规则统一描述数据可见性；子系统负责资源创建、资源标识、策略存储、业务角色、操作语义和最终执行。Helios 不需要理解词条内容、工单状态或文档正文，也不会因为用户属于某部门而自动在各系统创建资源。

## 2. 已确认的产品规则

| 项目 | 规则 |
| --- | --- |
| 组织结构 | 单公司，多级部门；部门为树形结构 |
| 成员关系 | 一个用户可属于多个部门，不分主次 |
| 默认可见性 | 公司内部公开，前提是用户已获准进入对应子系统 |
| 受限数据 | 归属部门始终可见，可额外授权其他部门和具体人员 |
| 部门负责人 | 可查看本部门及下级部门的受限数据，不能自动查看其他部门的受限数据 |
| 公司最高负责人 | 可查看全公司数据，仍需满足对应子系统的准入条件 |
| 操作权限 | 新建、编辑、删除等继续由子系统身份和角色控制 |
| 可见范围管理 | 仅归属部门的直接负责人和对应子系统管理员可以调整 |
| 人员调动 | 历史数据留在原部门，退出部门后失去通过该部门取得的权限；数据转移另行操作 |
| 实现位置 | Helios 内独立模块，暂不改其他系统 |

“所有数据”指通过子系统准入后可查看的业务数据，不意味着密码、密钥等敏感字段对所有用户公开。字段级保护仍由业务系统负责。

## 3. 权限分为三个独立维度

### 3.1 子系统准入

由现有项目成员、账号状态和子系统认证机制决定用户能否进入该系统。部门成员、负责人和公司最高负责人身份均不自动创建项目成员关系。

### 3.2 数据可见性

决定用户能否读取一份数据。数据默认公司内部公开，受限时按归属部门、共享对象、负责人层级判定。

### 3.3 操作能力

编辑、删除、导出等能力由子系统角色控制。部门成员和负责人身份不会自动使用户成为编辑者或子系统管理员。

统一关系：

```text
读取 = 账号有效 AND 子系统准入 AND 子系统读取能力 AND 数据可见
编辑/删除/导出 = 账号有效 AND 子系统准入 AND 对应操作能力 AND 数据可见
调整可见范围 = 账号有效 AND 子系统准入 AND 数据可见
               AND（归属部门直接负责人 OR 对应子系统管理员）
```

对子系统管理员增加一条窄范围权限：允许查询受限资源的最小权限管理信息并修改其可见范围，避免无法管理不可见资源；这不自动授予读取正文、下载附件的权限。该管理入口独立审计，调整后若管理员符合新范围才可读取内容。

父级部门负责人能查看下级受限数据，但不能仅凭父级身份修改其可见范围。公司最高负责人也不自动拥有编辑、删除、调整可见范围能力。

## 4. 组织模型与角色

### 4.1 部门

公司根节点作为稳定的虚拟根；实际部门有一个上级，可排序、改名、移动、停用。禁止循环和把部门移动到自身下级。成员可同时属于父部门和子部门，但两者各自独立。

部门层级仅用于负责人向下查看，不代表普通父部门成员自动访问子部门数据。

### 4.2 组织角色

| 角色 | 职责与边界 |
| --- | --- |
| 普通成员 | 通过所在部门获得受限数据可见性 |
| 部门负责人 | 必须是该部门有效成员；可有多人；具有本部门及下级数据查看范围 |
| 组织管理员 | 维护部门、成员和负责人；不自动取得业务数据权限 |
| 公司最高负责人 | 独立指定，可有多人；具有全公司数据查看范围 |
| 子系统管理员 | 沿用对应系统的管理员身份，仅管理该系统可见范围和功能 |

组织管理员不得通过普通组织编辑接口自行授予公司最高负责人或组织管理员身份。特权授予沿用 Helios 受保护的管理入口，并记录审计；禁止移除最后一名有效组织管理员。首次特权用户由显式初始化步骤指定，不从现有角色静默推断。

组织管理员可调整成员和负责人，因此具有间接影响访问权限的能力。相关操作必须展示影响范围并审计，不能将其描述为完全不影响业务数据的低权限角色。

### 4.3 成员变化

- 加入部门后，获得该部门作为归属部门或共享部门的数据可见性。
- 退出部门时，同一事务撤销该部门负责人身份和成员关系。
- 离开一个部门不影响仍有效的其他部门身份。
- 退出部门不影响公司公开数据，也不自动撤销明确授予个人的共享权限；界面必须提示仍然保留的个人授权，必要时单独撤销。
- 账号停用后，所有子系统访问均应拒绝，个人共享记录可以保留用于审计，但不能继续生效。
- 停用部门前要求处理有效成员、负责人、下级部门与数据归属。初期未接入业务系统时不得宣称已检查所有业务数据；未来接入后依登记系统逐一确认。

## 5. 数据归属与可见范围

### 5.1 归属规则

每个参与组织权限控制的资源有且仅有一个归属部门，与创建人分开记录。多人协作不使用多个归属部门，使用共享授权表达。

多部门成员在子系统新建资源时，若其引用既有权限策略单元，则继承该单元的归属；独立策略资源则由用户显式选择其所属的有效部门。不能按“第一个部门”自动决定，也不能接受未经验证的任意部门 ID。无部门用户可使用系统已准入的公开资源，但不能自行创建要求部门归属的独立策略资源。

业务系统中的个人私有数据、凭据等不能直接批量套用“默认公开”。后续接入必须先分类、预览并确认迁移规则，禁止把历史私有数据静默公开。

### 5.2 两种可见模式

| 模式 | 可见对象 |
| --- | --- |
| company | 通过子系统准入且具备读取能力的公司用户 |
| restricted | 归属部门成员、明确共享部门成员、明确共享人员、归属部门及其祖先部门负责人、公司最高负责人 |

第一版不实现显式拒绝列表，不支持排除归属部门某个成员，不支持“仅创建人可见”。多个允许来源取并集，避免既允许又拒绝的冲突。

共享给部门时只包含该部门直接成员，不隐含下级部门；共享部门的负责人也不能仅凭其管理其他下级部门而扩大授权。需要多个部门时明确勾选，界面分别显示父子部门。

### 5.3 判定流程

```text
1. 账号无效、子系统未准入或缺少相应业务操作能力 → 拒绝
2. 数据没有有效权限策略或归属异常 → 拒绝，进入修复流程
3. company → 可见
4. restricted，且满足以下任意一项 → 可见：
   a. 公司最高负责人
   b. 用户是归属部门直接成员
   c. 用户负责归属部门或归属部门的任一祖先部门
   d. 用户属于明确共享的部门
   e. 用户在明确共享的人员列表中
5. 其他情况 → 拒绝
```

第 1 步的业务操作能力针对当前操作检查。可见范围管理使用第 3 节的专用规则，子系统管理员的最小管理信息例外不开放正文。

### 5.4 单条资源与集合共用策略

不能要求所有子系统都有“知识库／项目／容器”。每种资源类型在接入时声明一种策略绑定方式：

1. 独立策略：一条词条、一张工单或一条资产记录分别绑定自己的策略，可以分别设置为公开或受限。
2. 共用策略：若业务确有集合结构，可以将集合设为策略单元，集合内资源引用同一策略；如一个词库内词条共用词库策略。

第一版每个受控资源只能解析到一份有效策略，不合并多层父子策略。资源类型的绑定方式由后端接入配置固定，不由普通用户随意切换。共用策略的资源只能在策略单元上调整权限；界面须说明修改影响整个集合，不能让用户误认为只修改当前一条。

从属内容如附件、处理记录、词条译文或评论，应按对应主资源解析同一策略。业务上的父子关系不自动等于权限继承，必须在接入映射中明确；独立策略词条不因展示在某个列表里就继承列表权限。未来若增加父子独立策略并存，须另定合并规则后再实现。

### 5.5 归属转移

转移归属与修改可见范围分为两个操作。建议仅子系统管理员执行转移，校验目标部门有效，预览随之获得或失去权限的人群，并记录原因。受限资源转移后，新归属部门必然可见，原部门只有仍在共享列表或满足其他条件时可见。操作必须显式确认共享列表的保留或清除，禁止隐式改变。

## 6. 数据表设计草案

所有 ID 使用现有 UUID 风格，时间使用带时区时间；以下为逻辑结构，不是本次数据库迁移。

### 6.1 Helios 负责的组织表

| 表 | 核心字段与约束 |
| --- | --- |
| departments | id、parent_id、code、name、sort_order、status、version、created_at、updated_at；code 公司内唯一，parent_id 外键；同级有效名称唯一 |
| department_memberships | id、department_id、user_id、role(member/manager)、created_at、updated_at；department_id + user_id 唯一，无主部门字段 |
| organization_privileges | user_id、privilege(org_admin/company_head)、granted_by、created_at；user_id + privilege 唯一 |
| organization_revision | 单公司一条记录，revision、updated_at；所有影响授权的组织变化递增 |
| organization_audit_logs | actor_id、action、target_type、target_id、before、after、reason、request_id、created_at |

负责人使用成员记录中的 manager 角色表达，避免负责人不是成员。部门删除采用受控停用和历史保留，不级联删除成员历史和审计。

初期通过 PostgreSQL 递归查询计算祖先和下级，无需额外闭包表。移动部门在事务中锁定必要组织记录、校验无环、更新版本并审计；数据量增长后再评估闭包表。

### 6.2 未来由业务系统持有的权限表

| 表 | 核心字段与约束 |
| --- | --- |
| resource_policies | id、system_id、resource_type、resource_id、owner_department_id、visibility(company/restricted)、version、updated_by、updated_at；system_id + resource_type + resource_id 唯一，此处资源标识指策略单元 |
| resource_policy_bindings | system_id、resource_type、resource_id、policy_id；前三字段组合唯一，每个受控资源绑定一份策略；独立策略资源绑定自己的策略，共用策略资源绑定所属单元策略 |
| resource_policy_departments | policy_id、department_id；组合唯一 |
| resource_policy_users | policy_id、user_id；组合唯一 |
| resource_policy_audit_logs | 操作者、资源、变更前后、组织版本、原因、请求 ID、时间 |

策略与业务数据放在同一业务数据库，以便列表过滤和原子更新。归属部门默认权限由规则计算，不重复写入共享表。跨服务 ID 无数据库外键，需要接入时校验并保留失效引用的修复流程。

Helios 不存所有业务记录的 ACL，也不直接访问各业务数据库。此划分保持组织模块独立，同时避免业务列表逐条远程鉴权。

system_id 必须由可信的子系统配置或服务身份确定，不接受客户端任意指定以切换权限域。resource_id 使用字符串兼容 UUID、整数和业务编码，但须由子系统规范化；不同类型或不同系统的同名 ID 不互通。策略与绑定变更应和业务资源创建、移动、删除使用同库事务，避免出现已有资源却没有可验证策略的窗口。

## 7. 与现有 Helios 模型兼容

现有 users.department 是字符串，不能表达多部门关系，也不能作为权限依据。保留兼容读取一段过渡期，新模型以 department_memberships 为唯一组织权限来源。

现有 project_memberships.role_in_project 继续表达项目／子系统身份。组织角色不替换项目角色，不直接修改现有 SSO 登录和会话规则。

迁移步骤：先统计旧部门字符串并生成映射预览，由管理员确认部门名称、层级、同名合并和成员归属，再事务导入。空值和不明确值列入待处理清单，不自动给任意部门。迁移可重复执行且不重复建关系；验证完成后逐步停止旧字段写入。旧字符串不得自动推断负责人。

## 8. 接口草案

以下路径为新增接口建议，须在开发前与现有路由校对。

| 方法与路径 | 用途与约束 |
| --- | --- |
| GET /api/v1/org/departments | 返回有效组织树和版本；普通用户不返回受保护的成员详情 |
| POST /api/v1/org/departments | 组织管理员新建部门 |
| PATCH /api/v1/org/departments/:id | 修改名称、排序、上级；要求 version，防止覆盖并发修改 |
| POST /api/v1/org/departments/:id/disable | 停用前置校验和审计 |
| GET /api/v1/org/departments/:id/members | 分页查询成员，按组织管理授权限制范围 |
| PUT /api/v1/org/departments/:id/members/:userId | 加入成员或设置 member/manager，仅组织管理员 |
| DELETE /api/v1/org/departments/:id/members/:userId | 退出部门，立即撤销对应负责人身份 |
| GET /api/v1/org/me | 当前用户部门、负责部门、组织特权与 revision |
| PUT /api/v1/org/privileges/:userId | 受保护的特权授予接口，拒绝普通组织管理员自行提权 |
| GET /api/v1/org/audits | 按角色受控查询组织变更记录 |
| POST /internal/v1/org/access-context | 未来供受信业务后端批量取得用户的组织访问上下文 |

访问上下文建议包含 user_id、account_status、department_ids、managed_department_ids、managed_subtree_ids、is_company_head、organization_revision。上下文不是业务授权的最终结果，不包含“所有操作均允许”的标记。

内部接口需要服务身份认证、限定可访问的项目和用途，禁止浏览器直接调用，也禁止把用户提交的身份或管理员布尔值当作可信事实。具体服务认证协议在正式接入设计中确定。

业务系统未来提供独立的策略读取／更新和归属转移接口；更新携带 expected_version，冲突返回 409，提交前重新校验当前权限，不能仅依赖打开弹窗时的校验结果。

## 9. 权限同步与撤销

组织上下文不长期固化在 JWT 中作为唯一授权来源。组织调整、部门移动、账号停用会影响权限，必须读取当前可信版本。

第一版接入建议每次受保护请求从 Helios 获取当前上下文，同一请求内复用；批量列表只取一次上下文，在业务数据库中统一过滤。Helios 不可用且无可验证的新鲜上下文时，受保护数据请求返回服务不可用，不放行也不伪装为空列表。

后续缓存和事件同步必须明确最大陈旧窗口、版本校验与故障策略后才能启用。下载、导出任务在执行时重新鉴权；长连接和异步任务不能无限沿用创建时权限。已下载到用户设备的数据无法通过权限撤销收回。

组织变更以事务提交为生效点；提交后开始的请求必须使用新版本，已经开始处理的请求采用其已验证版本。需要更严格中途撤销的操作，在真正交付内容前再次检查版本。

## 10. 页面与交互规划

本节为产品行为要求，不涉及本次页面实现。

- 组织管理：部门树配合部门详情、成员列表、负责人设置；成员管理展示用户全部部门，不出现“主部门”。
- 用户详情：平等的部门标签、负责人标记、组织特权。移除部门前提示受限数据权限将变化，并说明个人授权和公开内容可能继续可见。
- 部门移动：展示旧上级、新上级，以及负责人可见范围将随层级变化的提示。
- 可见范围弹窗（未来子系统）：提供“公司内部公开”“受限”两种模式；受限时固定展示归属部门，可追加部门和人员。
- 弹窗必须说明：“归属部门及其上级部门负责人、公司最高负责人仍可查看”，避免用户误认为仅勾选人员可见。
- 仅有编辑权限的用户看不到可见范围编辑入口；后端仍需独立校验。
- 子系统管理员权限管理入口只展示必要的资源标识、归属和策略，不因进入此页显示正文。
- 转移归属：展示权限变化，要求选择保留或清除额外共享并填写原因。
- 组织和权限修改提供保存中、冲突、失效对象、失败重试状态，禁止失败后界面显示为保存成功。

## 11. 场景验收矩阵

前提：除特别说明外，用户账号有效，已获子系统准入和相应业务操作能力。

| 场景 | 预期 |
| --- | --- |
| A 部门成员查看 B 部门 company 数据 | 允许 |
| A 部门成员查看 B 部门 restricted 数据，未共享 | 拒绝 |
| B 部门普通成员查看 B 部门 restricted 数据 | 允许，无须另行共享 |
| 父部门普通成员查看子部门 restricted 数据 | 拒绝，除非有其他允许来源 |
| 父部门负责人查看下级 restricted 数据 | 允许 |
| 父部门负责人修改下级数据可见范围 | 拒绝，除非也是直接负责人或该子系统管理员 |
| 用户兼属 A、B，查看两部门 restricted 数据 | 均允许 |
| 数据共享给 A，用户仅属于 A 的下级部门 | 拒绝，不自动继承共享 |
| 被共享人员只有读取角色，尝试编辑或删除 | 拒绝 |
| 编辑者修改可见范围，但不是直接负责人或子系统管理员 | 拒绝 |
| 子系统管理员没有受限正文查看权限 | 可管理最小策略信息，不得直接读取正文 |
| 公司最高负责人未获得子系统准入 | 拒绝进入或读取该系统数据 |
| 公司最高负责人具备准入和读取能力 | 可查看全部数据，不能自动编辑、删除或改可见范围 |
| 用户退出 B，但仍有直接个人共享 | 失去 B 成员来源，个人共享仍生效 |
| 用户退出 B，无其他授权来源 | 无法再看 B restricted 数据；仍可查看公开数据 |
| 账号停用、旧会话仍存在 | 拒绝访问 |
| 部门改挂到新父部门 | 旧祖先负责人失去继承来源，新祖先负责人获得；其他授权独立计算 |
| 受限容器附件直链、搜索摘要、导出、数量统计 | 与容器采用相同可见性过滤，不能绕过 |
| 提交伪造部门 ID、用户 ID、管理员标记 | 后端按可信身份和当前组织验证，拒绝越权 |
| 策略并发修改 | 版本冲突，不能静默覆盖 |
| 组织服务故障 | 受保护请求返回服务不可用，不降级放行 |

测试必须覆盖多授权来源的并集与撤销、层级移动、跨部门 ID 枚举、批量列表和单项详情的一致性。未授权资源对外避免泄露存在性，统一使用适当的 404；管理员策略入口按其管理权限另行处理。

## 12. 分阶段交付

1. 设计评审：确认本文规则、子系统管理员的最小管理信息例外、默认容器继承与归属转移流程。
2. Helios 组织模块：数据库显式迁移、部门和成员管理、组织特权、审计、旧字段映射预览；独立验收，不改变任何业务系统数据可见性。
3. 接入协议：服务身份认证、组织上下文、版本与故障规则、通用鉴权用例。协议交付不等于系统已完成隔离。
4. 单系统试点：另行选择系统和资源容器，审查存量私有数据，补齐列表、详情、搜索、附件和导出等所有入口，验证撤销后再启用。

后续开发以显式数据库迁移实施，不借启动过程自动变更权限模型；回滚组织功能时保留关系与审计数据。已接入业务系统不得因组织模块不可用或回滚而把 restricted 数据改为公开。

## 13. 核心结论

组织归属决定受限数据的允许来源，部门层级仅为负责人提供向下查看能力。业务身份决定操作能力，公司公开也受子系统准入限制。数据可见性和业务角色必须同时满足，任何一方都不能替代另一方。

## 14. 用一家公司讲解全部权限维度

本节的“知识系统、手册、文档”仅是一种业务映射示例：内容由假设的知识子系统创建，不由组织模块创建。它们不是通用模型的对象名称。跨子系统的精确表达见第 15 节。

本节穷举规则类别和关键组合，不承诺穷举任意人数、部门和业务类型的无限组合。新增业务类型仍需用同一判定规则验证。以下案例均是假设未来子系统完成接入后的行为，并非现有系统已经具备这些功能。

### 14.1 示例组织与人物

```text
公司（公司最高负责人：周总）
├─ 技术部（负责人：老陈）
│  ├─ 研发部（负责人：老李；成员：小张、小王）
│  │  └─ 服务端组（负责人：老赵；成员：小刘）
│  └─ 测试部（负责人：老孙；成员：小吴、小王）
├─ 产品部（负责人：老钱；成员：小林）
└─ 财务部（负责人：老郑；成员：小何）
```

负责人同时是所负责部门的成员；小王同时属于研发部与测试部，无主次。老陈只属于技术部，不额外加入研发部。小刘只属于服务端组，不自动成为研发部直接成员。

额外设置小许为组织管理员，小马为知识系统管理员，两者无其他部门负责人或公司最高负责人身份。

示例子系统称“知识系统”，其角色示例为：阅读者只能看，编辑者能看、新建和编辑，业务管理员能看、新建、编辑、删除和导出。这些是用于解释的能力配置，不替现有子系统定义角色。可见范围管理另按组织规则判定。

除特别说明外，示例人员都有知识系统准入和读取能力；提到编辑时另外注明编辑能力。

设三份数据：

| 数据 | 归属 | 可见模式 | 额外共享 |
| --- | --- | --- | --- |
| 入门手册 | 研发部 | 公司内部公开 | 无需共享 |
| 研发计划 | 研发部 | 受限 | 无 |

### 14.4 谁可以编辑、删除和管理可见范围

以下各项默认数据本身可见，除非明确说明不可见。

| 编号 | 例子 | 结果与原因 |
| --- | --- | --- |
| A01 | 小张是阅读者，想编辑研发计划 | 不可以，部门成员身份不提供编辑能力 |
| A02 | 小张是编辑者，编辑研发计划 | 可以，可见且有编辑能力 |
| A03 | 小林是编辑者，编辑联调方案 | 可以，按本方案，共享提供可见性，再叠加子系统编辑能力 |
| A04 | 小林是编辑者，编辑未共享的研发计划 | 不可以，有编辑能力但数据不可见 |
| A05 | 小林可看联调方案，但其角色没有删除能力 | 不可以删除 |

| A07 | 老李是阅读者，想编辑研发计划 | 不可以，负责人身份不自动授予内容编辑能力 |
| A08 | 老李是阅读者，想调整研发计划可见范围 | 可以，只要有准入和读取能力，直接负责人有独立的范围管理权限 |
| A09 | 小张是编辑者，想把研发计划改为公开 | 不可以，不是直接负责人或子系统管理员 |
| A10 | 老陈想调整研发计划的可见范围 | 不可以，祖先负责人仅继承查看，不继承范围管理 |
| A11 | 周总想改研发计划的可见范围 | 不能仅凭公司最高负责人身份修改；需同时具备直接负责人或子系统管理员身份 |
| A12 | 周总仅是阅读者，想删除研发计划 | 不可以，公司最高负责人只扩展可见性 |
| A13 | 小马是知识系统管理员，想管理研发计划策略 | 可以，经专用入口查看最小管理信息并修改策略 |
| A14 | 小马没有研发计划可见来源，想直接下载正文附件 | 不可以，管理员策略入口不自动授权内容读取 |
| A15 | 小马管理另一个子系统的数据策略 | 不可以，管理员身份按子系统隔离 |
| A16 | 小许仅有组织管理员身份，想看研发计划 | 不可以，不自动获得业务数据权限 |

### 14.5 新建、公开与受限切换

| 编号 | 例子 | 结果与原因 |
| --- | --- | --- |
| P01 | 小张在已有受限容器中新建文档 | 有新建能力则可创建，新文档继承容器受限策略 |
| P02 | 小张新建独立容器，没有现成策略 | 有新建能力则按默认公司内部公开创建，归属需经过后端验证 |
| P03 | 小王新建无父容器的数据 | 显式选择研发部或测试部；两部门无主次，不按列表顺序默认归属 |
| P04 | 小张选择财务部作为新数据归属 | 拒绝，他不属于财务部；管理员代建需单独授权的操作，不能借普通新建接口绕过 |
| P05 | 普通编辑者希望新建一份立即受限的独立容器 | 当前方案不能由其自行设受限，需由直接负责人或子系统管理员创建受限容器，再让其录入内容 |
| P06 | 老李将研发计划从公开改为受限 | 可以，其他部门没有其他授权的人立即失去后续读取权限 |
| P07 | 老李将受限数据改回公开 | 可以，提交前提示范围将扩大至所有已准入用户 |
| P08 | 受限内容改为公开，再改回受限 | 建议改为公开时清除额外共享列表；改回受限时重新选择，防止旧共享静默恢复。此为实施建议 |
| P09 | 普通用户修改创建人字段以取得权限 | 不可以，创建人不决定数据可见性或范围管理权限，字段也不能任意篡改 |
| P10 | 已经限制整个容器，想单独公开一个附件 | 第一版不支持，附件继承同一策略 |

P05 是默认公开与限制范围管理者带来的实际边界。需要保密的内容不能先公开录入再等待负责人修改，应先建立受限容器。若业务需要普通成员直接发起保密内容，应另行确认“创建时申请受限／预设受限模板”等流程，不能偷偷放宽范围管理规则。

### 14.6 调岗、离职、负责人和部门结构变化

| C05 | 老李退出研发部 | 同一事务撤销研发部负责人身份；失去该负责人和成员来源 |

| C07 | 研发部新增第二名负责人 | 两名直接负责人都可查看并管理研发部数据可见范围 |
| C08 | 小刘从服务端组加入研发部，但仍保留服务端组身份 | 可通过直接成员关系看研发计划，两部门并列，无主次 |
| C09 | 研发部从技术部移动到产品部下 | 老陈失去该祖先继承来源；老钱获得研发部及其下级受限数据查看来源 |
| C10 | 部门改名 | ID 不变，数据归属和权限不变 |
| C11 | 小吴账号停用，但仍有个人共享和旧登录会话 | 拒绝访问，账号有效性优先 |
| C12 | 删除仍有成员、下级或数据的部门 | 拒绝直接删除；先处理关联，保留审计 |
| C13 | 部门被受控停用后仍有遗留策略引用 | 进入修复流程，不将这些内容自动公开 |
| C14 | 公司最高负责人身份被撤销 | 失去公司级查看来源，成员、共享等其他来源独立计算 |

### 14.7 数据转移、复制和多个系统

| 编号 | 例子 | 结果与原因 |
| --- | --- | --- |
| T01 | 研发计划转移归属到产品部 | 经子系统管理员显式操作后，产品部成员获得基础可见性；研发部成员不再自动可见 |
| T02 | 转移时选择保留额外共享，列表中仍有小吴 | 小吴的个人共享继续生效 |
| T03 | 转移后老李没有其他授权 | 老李失去原直接负责人带来的查看和范围管理能力 |
| T04 | 将受限文档复制到另一个容器 | 属于新资源的创建和可能的信息传播；建议第一版跨容器复制只允许有源读取、目标新建且源范围管理资格的人员操作，再明确确认目标策略，此为接入建议 |
| T05 | 将受限内容移到公开容器 | 可能扩大可见范围，不能只检查普通编辑能力；需按归属转移和范围变更流程评审执行 |
| T06 | 小林在知识系统是编辑者，在工单系统是阅读者 | 可编辑知识系统可见内容；不能因该身份编辑工单 |
| T07 | 同一部门在两个系统都有数据 | 组织关系相同，但准入、角色、资源策略分别判定 |
| T08 | 公司最高负责人看某系统私有凭据字段 | 组织范围不取消字段保护，该系统仍须按专门规则隐藏凭据 |

### 14.8 搜索、附件、导出、通知与故障

| 编号 | 例子 | 结果与原因 |
| --- | --- | --- |
| E01 | 搜索研发计划标题和摘要 | 无权用户不能看到标题、摘要或匹配片段 |
| E02 | 首页显示“研发部有 12 份受限文档” | 数量也要按访问范围过滤，避免泄露受限存在性 |
| E03 | 粘贴受限文档详情 URL | 后端仍检查资源权限，知道 URL 不获得权限 |
| E04 | 粘贴附件地址、缩略图地址 | 与父资源同策略；不能使用永久公开静态路径绕过 |
| E05 | 批量导出混合可见和不可见内容 | 查询阶段过滤并按导出策略处理，不能导出越权记录；不得仅检查导出按钮权限 |
| E06 | 开始导出后用户被移出部门 | 异步执行及交付前按当前规则复核，不能永久沿用任务创建时权限 |
| E07 | 通知消息或邮件包含受限摘要 | 生成和发送时检查收件人权限；已发送到外部渠道的内容无法撤回，建议通知仅含必要标识和需登录访问的链接 |
| E08 | 权限撤销后页面已经显示正文 | 后续请求拒绝；已显示或下载的内容无法可靠收回，前端不应承诺能收回 |
| E09 | 组织服务临时不可用 | 请求失败并提示稍后重试，不因鉴权故障放行受限内容 |
| E10 | 两名负责人同时修改共享范围 | 后提交者遇到版本冲突，刷新比较后重试 |
| E11 | 用户在打开权限弹窗后被撤销负责人身份 | 保存时重新鉴权，拒绝旧身份提交 |
| E12 | 内容数据库缺少策略记录或归属损坏 | 拒绝并修复，不当作默认公开 |
| E13 | 页面缓存、浏览器后退、服务端缓存命中旧数据 | 缓存须按用户和权限版本区分；后续交付重新校验，不能跨用户复用受限响应 |

### 14.9 管理员的真实权限边界

“不自动获得查看正文权限”不等于“绝对无法取得正文”。组织管理员可以调整成员和负责人，子系统管理员可以修改可见范围，因此他们可能通过管理操作使自己获得访问权。

例子：小马不能直接读取研发计划，但他作为子系统管理员把自己加入共享列表后，就可以按新策略读取。小许把自己加入研发部后，也能通过成员关系读取。按当前选择，这些属于可信管理能力，必须被审计，不能宣称技术上隔绝了管理员。

第一版建议保存操作者、变更原因、前后值、时间和请求 ID，并支持检索“管理员为自己增权”的记录。如果公司要求管理员也不能自行取得数据权限，需要另外增加审批、双人复核或更强的职责分离；本次未选择这些流程，不默认加入。

### 14.10 从任意新例子得出结果

遇到本文没有同名列出的业务例子，按以下顺序检查，结果即可确定：

1. 用户账号有效吗？能进入这个子系统吗？
2. 资源归属和策略有效吗？当前操作需要什么业务能力？
3. 资源是公开还是受限？受限时，成员、共享、负责人或公司级身份是否至少命中一项？
4. 用户是在读内容、编辑、删除、导出，还是修改可见范围？对照不同的操作资格。
5. 是否涉及子项继承、复制、移动、归属转移或异步任务？检查其专门规则。
6. 是否存在组织或策略变更？使用当前可信状态，不只相信页面或旧令牌。

这样可以覆盖规则的组合，而不用为每一个人员姓名和部门排列编写一套不同权限代码。

## 15. 通用资源的跨系统示例与接入约定

### 15.1 同一条权限规则，作用于不同业务对象

设小张属于研发部，小林属于产品部，两人均取得相应系统准入和读取能力。以下资源采用独立策略：

| 资源身份（示例） | 创建位置及动作 | 策略 | 小林读取结果 |
| --- | --- | --- | --- |
| terminology / term_entry / T100 | 小张在术语系统创建词条 T100 | 研发部归属，公司内部公开 | 可以读词条 |
| support / ticket / T100 | 小张在工单系统提交工单 T100 | 研发部归属，受限，无额外共享 | 不可以读工单 |
| knowledge / document / T100 | 小张在知识系统创建文档 T100 | 研发部归属，受限，共享给产品部 | 可以读文档 |
| assets / asset / T100 | 小张在资产系统登记资产 T100 | 研发部归属，受限，直接共享给小林 | 可以读资产记录 |

四条资源的 resource_id 都是 T100，但它们位于不同权限命名空间，不共享策略。创建者姓名也不使四条资源自动互通。此处系统名和类型名为示例编码，不是已存在的服务配置。

把词条 T100 改成受限，只影响该词条及其明确绑定同策略的从属内容，不影响同名工单，也不默认影响全部词条。若系统选择词库共用策略，则应在词库上修改，并影响所有绑定该词库策略的词条，界面必须明示。

### 15.2 相同的可见性，不同的业务操作

小林可以读某个共享资源，不表示他可以做该资源的所有动作：

| 子系统动作 | 还需满足的业务条件示例 |
| --- | --- |
| 编辑词条 | 术语系统的词条编辑资格 |
| 审核词条 | 术语审核资格，且词条处于待审核状态 |
| 关闭工单 | 工单处理资格，且当前状态允许关闭 |
| 报废资产 | 资产报废资格，且满足资产状态或审批要求 |

这些条件由各子系统判定。统一模型为：账号有效且子系统准入 + 资源可见 + 子系统允许该用户对该资源执行该动作。动作的业务条件不由部门关系替代。

新建与现有资源操作分开：新建时对象尚不存在，应检查新建能力、目标策略单元访问资格及归属合法性，不能先用不存在的资源 ID 做读取鉴权。新建资源与策略绑定须原子提交。只有新建成功的受控资源才进入后续读取／更新流程。

### 15.3 通用权限描述示例

以下是概念结构，不是已经发布的 API：

```json
{
  "resource": {
    "system_id": "terminology",
    "resource_type": "term_entry",
    "resource_id": "T100"
  },
  "policy_id": "policy-example",
  "owner_department_id": "department-rd",
  "visibility": "restricted",
  "shared_department_ids": ["department-product"],
  "shared_user_ids": [],
  "version": 1
}
```

其中没有“手册正文”“词条释义”或“工单状态”，这些属于子系统数据。用户身份、组织上下文、业务能力及策略均由后端可信来源解析，不接受前端提交的“已授权”结论。

### 15.4 每个子系统接入前必须提交的映射表

1. 系统标识、资源类型和稳定资源 ID；哪些数据不适用公司公开规则（如私有凭据）。
2. 每类资源使用独立策略还是集合共用策略；关联内容如何解析同一策略。
3. 归属部门从何而来；新建、导入、同步、后台任务都如何创建策略绑定。
4. 系统准入、读取和各业务动作如何判定；“子系统管理员”在该系统中具体对应哪个受信身份。
5. 列表、详情、搜索、统计、附件、API、导出和通知如何执行相同过滤。
6. 资源复制、移动、删除、恢复和系统间传输如何处理策略；禁止把源系统授权直接当作目标系统授权。
7. 存量资源迁移预览、权限撤销、审计、故障与回滚方案。

这张表没有确定前，不宣称该子系统已经受组织权限保护。通用模型统一判定规则，不强制所有业务系统使用相同的业务对象、界面或创建流程。
